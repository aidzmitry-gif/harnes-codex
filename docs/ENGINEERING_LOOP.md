# Инженерный loop: доказательство → изменение → доказательство

## 0. Создать рабочую карточку

Для каждой нетривиальной задачи создать `.harness/work/<id>.md` из шаблона. Это не бюрократия: карточка — внешняя память агента и защита от дрейфа цели.

## 1. Discovery: понять текущую систему

Собрать только факты, нужные для решения: инструкции, стек, точки входа, путь запроса/данных, существующие тесты, git-статус. Разделить факты и предположения. Не менять файл, пока не определены владелец поведения и тестируемая граница.

**Выход:** заполнены «Наблюдения» и «Гипотеза»; назван файл/модуль, где изменение вероятнее всего должно жить.

## 2. Intent check: отсечь неверное направление до правки

Сформулировать в карточке:

- пользовательский исход и один наблюдаемый критерий успеха;
- что намеренно не меняется;
- входы, выходы и инварианты затронутого контракта;
- самый дешёвый эксперимент, который опровергнет гипотезу;
- возможный откат.

Если нельзя описать ожидаемый эффект одной проверкой, задача ещё исследуется. Если эксперимент опроверг гипотезу — отметить это и вернуться к Discovery, а не «дожимать» исходное решение.

## 3. Impact assessment

Оценить каждый пункт: API/совместимость, схема и данные, авторизация/секреты, производительность, параллелизм, наблюдаемость, внешние зависимости. Присвоить риск: низкий, средний или высокий. При высоком риске план проверки и отката должны быть готовы до кода.

## 4. Preflight

Запустить:

```powershell
.\scripts\Invoke-HarnessGate.ps1 -Stage prechange
```

Исправить блокирующие пункты. Предупреждения допустимы только с записанной причиной в карточке.

Для Goal перед записью worker и после изменения плана, авторизации или реестра агентов проверьте единственную исполняемую проекцию work item:

```powershell
python .\goal_runner_validator.py check .harness\work\<chain>.passport.json
```

До измеряемого запуска назначьте baseline/treatment. На meaningful checkpoint используйте `harness_metrics.py record` только со структурированным событием: фактические runtime tokens или оба `null`, без transcript, free text и оценок. Запускайте paired compare только при валидных парах; deterministic benchmark — regression evidence, не доказательство реальной token economy.

## 5. Implement: минимальный вертикальный срез

Сначала добавить/уточнить тест либо другой воспроизводимый оракул. Затем реализовать минимальную версию. После каждого логически завершённого среза выполнить узкую проверку. Не добавлять «полезные заодно» изменения.

### 5.1 Лестница лени: остановиться на первой достаточной ступени

Перед реализацией выбрать и записать первую ступень, которая полностью выполняет контракт:

1. не делать — YAGNI;
2. stdlib или возможность языка;
3. нативный примитив платформы;
4. существующая зависимость проекта;
5. одна прямая строка;
6. минимальный работающий код.

Не подниматься выше ради будущих сценариев. Предпочитать удаление, меньше файлов и отсутствие абстракций «про запас». Не применять упрощение к trust boundaries, защите данных/денег, security, accessibility, транзакциям, конкурентности и явно запрошенному поведению. Ограниченное намеренное упрощение помечать `ponytail:` с измеримым порогом и путём апгрейда.

## 6. Verify: пирамида проверок

1. Целевая проверка контракта.
2. Быстрые автоматические проверки.
3. Полный набор, нужный уровню риска.
4. Пост-изменительный gate: `-Stage postchange`.
5. Ручная проверка сценария, если автоматизация не покрывает наблюдаемый исход.

При падении не маскировать тест, не ослаблять assertion ради зелёного статуса. Локализовать причину, записать вывод и вернуться к минимальному срезу.

## 7. Diff review: отдельная фаза мышления

Прочитать `git diff` и ответить:

- Каждая строка нужна задаче?
- Сохранены ли ошибки, границы, значения по умолчанию и обратная совместимость?
- Нет ли секретов, логирования данных, новых прав или сетевых вызовов?
- Соответствует ли документация фактическому поведению?
- Можно ли быстро откатить изменение?

Затем выполнить `-Stage release` и внести фактические команды/результаты в карточку.

После correctness-review выполнить отдельный simplify-review: для каждого нового файла, зависимости, абстракции, ветки и конфигурации заново пройти лестницу лени. Удалить то, для чего нижняя ступень сохраняет тот же контракт. Не маскировать этим проходом дефекты корректности или безопасности.

## Решение по результату

| Сигнал | Действие |
| --- | --- |
| Гипотеза подтверждена, проверки зелёные | продолжить к следующему срезу или передать результат |
| Гипотеза опровергнута | откатить срез, обновить карточку, вернуться к Discovery |
| Неполное доказательство | не расширять изменение; явно обозначить риск или запросить данные |
| Проверка падает | локализовать, исправить или остановиться; не объявлять готовность |
