# Распространение проверенного Harness

Один опубликованный immutable commit/tag — источник версии. На каждом ПК нужна
локальная копия той же версии; запуск из общей сетевой папки и синхронизация через
облачную папку поверх работающего checkout не поддерживаются.

## Что распространяется

`harness_distribution.py` управляет только фиксированными 18 core-файлами:
Python validators/planner/radar/metrics, gate, инженерный loop и шаблоны.
Python-модули копируются в корень проекта: `acceptance_gate.root()` вычисляется
по расположению файла. Ссылка на центральный Python helper направила бы evidence
не в тот проект. Глобальные skills подключаются отдельно существующим
`scripts/Install-GoalRunner.ps1`.

AGENTS.md, CLAUDE.md, harness.config.json, CI, .env, пользовательские исходники,
контекст, work items, acceptance, metrics и живой runtime не распространяются.
Отсутствующий профиль не заполняется выдуманными тестами: результат честно содержит
`profileConfigured=false`, а `projectAcceptance=not-run` даже при правильных хешах.
Владелец проекта выбирает проверяемый уровень по docs/ADOPTION.md.

## Один ПК: предварительная проверка и применение

1. Получите опубликованную версию в отдельный чистый локальный checkout. Проверьте
   remote и точный commit/tag. Не подменяйте существующий грязный checkout; не
   используйте force/reset. Не обновляйте source или global skills во время задач.
2. Сверьте локальные project paths по Codex и Graphify `sources.local.json`.
   Graphify является картой: старый/отсутствующий путь не становится новой целью.
   Не публикуйте локальный реестр или auth/config/state ПК в GitHub.
3. Подготовьте schema-1 JSON с `projects`: каждый элемент содержит `name`, абсолютный
   `path`, `hostId: "local"`; `deferredReason` явно исключает цель из записи.
   Неизвестные/повторные поля, неверные типы, опечатки и пересечение активных roots
   отклоняются до первой записи. Вложенную цель нужно явно отложить.
   Не включайте сетевые shares, вложенные копии одного репозитория или source checkout
   как проект установки. Сначала прочитайте локальные инструкции, проверьте git и
   завершение активных задач. Различающиеся локальные версии требуют review.
4. Из Windows PowerShell выполните preview (не меняет проекты):

   ```powershell
   .\scripts\Update-HarnessProjects.ps1 -RegistryPath <local-registry.json>
   ```

5. После проверки списка и подтверждённого idle примените:

   ```powershell
   .\scripts\Update-HarnessProjects.ps1 -RegistryPath <local-registry.json> -Apply -IdleConfirmed
   ```

   `-WhatIf` также запрещает применение. Результат JSON печатается для каждой цели;
   exit 2 означает наличие конфликтов/недоступных/отложенных целей, не общий успех.
   `IdleConfirmed` — утверждение вызывающего владельца, не детектор процессов.

Одиночные `plan`, `apply --plan-hash ... --idle-confirmed`, `verify` команды доступны
в `python harness_distribution.py --help`. Обе директории передаются абсолютными.
Скрипт offline: не скачивает релизы, не выполняет профили/команды проектов, не меняет
модель, effort, agent cap, права или active automations.

## Версия, конфликты и восстановление

`harness-release.json` содержит releaseId, fixed file list, SHA-256 файлов и
aggregate bundleHash. Это проверка целостности, не криптографическая подпись и не
источник разрешения: доверять нужно проверенному release commit в вашем репозитории.
Автор выпуска получает JSON через `release --source <absolute-root> --version <id>`;
после изменения любого managed файла manifest обновляется и проверяется заново.
В source checkout `.gitattributes` закрепляет LF только для этих 18 файлов;
иначе Windows `core.autocrlf` изменил бы байты после клонирования и нарушил хеши.
Настройки Git целевого проекта не переписываются: если его последующий checkout
преобразует managed файлы в CRLF, следующий preview обнаружит конфликт, а не
молча примет изменённые байты.

В каждом проекте `.harness/distribution.json` хранит ту же точную версию и хеши.
Новые файлы создаются; совпадающие байты можно принять под управление. Неизвестный
одноимённый файл или изменение/удаление managed файла блокирует весь проект без
частичной установки. Никакого автоматического «это старая похожая версия» нет.
Повтор проверенной установки — no-op. Новый payload/состояние инвалидируют plan hash.
`verify` доказывает соответствие локальной receipt, не актуальность относительно
другого релиза. Для этого нужен `plan` с проверенным source. Wrapper различает
`installed`, `current`, `conflict`, `deferred`, `unavailable`; preview остаётся
`planned`, а центральная рабочая копия отмечается `source-checkout`.

Cooperating installers сериализуются lock-каталогом `.harness/.distribution-lock`.
Это не блокировка редакторов, процессов Codex или другого пользователя: внешний
caller отвечает за idle и отсутствие параллельных writers. Во время обновления
потребители не должны читать частично заменённый набор файлов.

Перед записью сохраняются только заменяемые managed байты и журнал транзакции в
`.harness/distribution-backups/<uuid>/`. При обычном сбое прежние байты возвращаются;
новые собственные файлы убираются. При crash или конкурентном редактировании lock
и backup сохраняются: проверить журнал и хеши, восстановить только точные managed
пути в отдельной одобренной recovery-операции. Не удалять lock/backup автоматически.
Успешные backups также сохраняются до отдельного решения об очистке.

## Другие ПК и автоматическое распространение

На каждом Windows-ПК один раз нужны Git, Python 3.11+ и локальная установка Codex.
После клонирования того же проверенного релиза прочитайте README об установке
Goal Runner и выполните существующий installer сначала с `-WhatIf`. Он не должен
перезаписывать чужие конфиги/roles/junctions; конфликт требует отдельного решения.
После изменения глобального config нужна новая сессия/перезапуск Codex.
Данный PowerShell installer использует Windows junctions; macOS/Linux global setup
нужно адаптировать и проверить отдельно, хотя offline Python core переносим.

Текущий CLI — механизм управляемого применения, не remote updater и не scheduler.
Планировщик может вызывать его только после настройки фиксированного доверенного
источника, локального реестра, проверки idle и границ разрешения. Нельзя считать
ежедневный опрос или скачанный commit установленным релизом. ПК без подключения
остаётся `unavailable`; setup и контрольный запуск на нём обязательны.
