# Work item: workspace-baseline

## Цель

- Проблема: аудит `D:\6 Проекты` показал разный уровень защиты: ERP имеет исполняемые гейты, а часть самостоятельных проектов — только документацию или вовсе не имеет harness.
- Ожидаемый исход для пользователя: общий harness можно подключить к новому или существующему проекту с профилем риска и объективным acceptance gate, не заменяя локальные правила.
- Не входит в задачу: правка, настройка, запуск тестов или перенос hooks в чужие проекты; доступ к production; унификация ERP-worktree.

## Контракт и доказательства до правки

- Наблюдения: ERP использует JSON acceptance gate с повторным запуском команд; SEO и Логолэнд содержат полезные правила, но у них нет такого переносимого исполняемого гейта.
- Гипотеза: лёгкий JSON-профиль и standalone Python gate позволят привносить проверяемость по одному проекту, не копируя весь fleet-контур ERP.
- Оракул: gate создаёт критерии, не считает пустой/ручной критерий без evidence пройденным и возвращает ошибку для отсутствующего gate; шаблоны валидны как JSON.
- Инварианты / совместимость: ничего вне текущего репозитория не меняется; команды проверок запускаются только по явному указанию в JSON.

## Карта воздействия

- Компоненты и потребители: будущие проекты, агенты и разработчики.
- Данные / миграции: нет.
- Безопасность / права / секреты: gate не читает `.env`; выполнение команд — только из локального JSON, созданного доверенным пользователем.
- Внешние зависимости: Python 3 для acceptance gate; PowerShell для существующего базового gate.
- Риск: низкий.
- Откат: удалить добавленные файлы одним коммитом.
