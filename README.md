# Harness для агентной разработки

Этот репозиторий задаёт безопасный и экономный способ, по которому агент (и человек) ведёт разработку: сначала собирает доказательства, затем делает минимальное обратимое изменение и проверяет результат на уровне контракта, интеграции и регрессий.

Главная инструкция для агента — [AGENTS.md](AGENTS.md). Полная модель процесса — [docs/ENGINEERING_LOOP.md](docs/ENGINEERING_LOOP.md). Рабочие артефакты по каждой задаче сохраняются в `.harness/work/` и не должны попадать в коммиты с продуктовым кодом.

## Быстрый старт

1. Скопируйте `templates/work-item.md` в `.harness/work/<id>.md`.
2. Заполните цель, контракт, риски и критерии приёмки до первой правки.
3. Запустите предварительную проверку:

   ```powershell
   .\scripts\Invoke-HarnessGate.ps1 -Stage prechange
   ```

4. Внесите один минимальный вертикальный срез и запустите:

   ```powershell
   .\scripts\Invoke-HarnessGate.ps1 -Stage postchange
   ```

5. Перед передачей результата выполните `-Stage release` и заполните доказательства в work item.

## Передача контекста между задачами

Вызовите `$context-handoff`, когда задача стала длинной, уже сжималась или должна продолжиться в чистой задаче. Навык:

1. обновляет один канонический журнал проекта (`.harness/CONTEXT.md` по умолчанию или путь из локальных инструкций);
2. исключает transcript, скриншоты, browser state, полные логи и секреты;
3. показывает короткий title и стартовый prompt;
4. создаёт новую задачу только после подтверждения;
5. проверяет, что новая задача прочитала handoff, и только затем отдельно предлагает архивировать старую.

В утверждённой цепочке `$goal-runner` действует bounded chain mode: одно стартовое разрешение может покрывать чистые задачи-продолжения той же Goal. Предыдущие задачи становятся неактивными, но остаются открытыми до итоговой проверки; архивирование всей зарегистрированной цепочки выполняется только по отдельной финальной команде пользователя.

Не используйте fork для экономии контекста: он переносит историю исходной задачи. Канонический исходник навыка находится в `.agents/skills/context-handoff`; для работы во всех проектах подключите его в пользовательский каталог `~/.agents/skills/context-handoff` ссылкой или junction.

### Автонапоминание после compact

`scripts/Install-ContextHandoffReminder.ps1` устанавливает глобальный `SessionStart` hook с matcher `^compact$`. После ручного или автоматического сжатия hook добавляет только короткое напоминание предложить `$context-handoff`; он не читает transcript, не пишет project context и не создаёт/архивирует задачи.

Installer идемпотентен, проверяет TOML до замены и сохраняет исходный глобальный конфиг как `~/.codex/config.toml.bak-context-handoff-reminder`.

## Оркестрация большой Goal

`$goal-runner` превращает большую цель в DAG из измеримых подцелей. До запуска он показывает количество подцелей, ожидаемый результат каждой, зависимости, параллельные волны, роли/модели агентов, worktree ownership и проверки. После одного подтверждения оркестратор распределяет общий пул между готовыми подцелями, проверяет понимание task contracts, интегрирует доказательства и при необходимости продолжает Goal через `$context-handoff`.

Перед первой записью worker создайте один исполняемый снимок плана рядом с work item (`.harness/work/<chain>.passport.json`) и проверьте его. Markdown work item остаётся журналом решений, а JSON — только его проверяемой проекцией:

```powershell
python .\goal_runner_validator.py check .harness\work\<chain>.passport.json
git hash-object .harness\work\<chain>.passport.json
```

Повторяйте проверку до каждой записи worker и после изменения плана, авторизации или реестра агентов. Для измеряемого запуска заранее задайте короткие ID `baseline` и `treatment`. Телеметрию пишите только на контрольных точках запуска/принятой подцели; токены — только фактические значения runtime либо оба `null`:

```powershell
python .\harness_metrics.py record --file .harness\metrics\<chain>.jsonl --from .harness\work\<event>.json
python .\harness_metrics.py compare --file .harness\metrics\<chain>.jsonl --baseline baseline --treatment treatment
python .\harness_metrics.py task --file .harness\metrics\<chain>.jsonl --chain <CHAIN> --work-item <id>
```

В отчёт задачи входят токены, неудачные попытки и процент свежих критериев приёмки.
`failedAttempts` включает schema 2; старые события schema 1 остаются читаемыми.
Токены/неудачи без полного покрытия — `null` плюс известная часть; дубликат runId
отклоняется. Процент — свежие PASS / все критерии по той же проверке, что используют
`status` и Goal unlock. `task` не запускает acceptance-критерии; отсутствующий журнал
или acceptance дают «нет данных».
Используйте CLI, установленный в измеряемом проекте: gate и fingerprint привязаны
к каталогу `acceptance_gate.py`, а не к произвольному cwd.

Исходный профиль моделей для новых задач: **GPT-6 Luna xhigh** — ограниченная
реализация, тесты и ясный поиск (сохранён прежний effort при миграции);
**GPT-6 Sol high** — координация и кодинг, требующий суждения; **GPT-6 Astra
xhigh** — неоднозначные контракты и итоговая проверка высокого риска. Для простой
низкорисковой задачи можно согласовать Luna low/medium с адресным оракулом, а
затем сравнить свежую приёмку и фактический расход на одинаковых входах. Это
гипотеза маршрутизации, не доказанная экономия. План содержит точные `model`
и `reasoningEffort`, проверяет их и передаёт в `launch`; старые Terra/Sol/Luna 5.6
паспорта сохраняются. В этом интерфейсе Goal допускает для Sol/Luna `low…max`:
API-поддержка `none` не означает её доступность через Codex-делегирование.
Проверяйте доступность конкретной модели и фиксированную модель установленной
роли до запуска: правка исходников не переключает уже запущенного агента и не
устанавливает профиль глобально или в других проектах.
Основание специализации моделей: [выбор модели OpenAI](https://developers.openai.com/api/docs/guides/model-selection),
[Sol](https://developers.openai.com/api/docs/models/gpt-6-sol) и
[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna); конкретный Codex runtime проверяется отдельно.

Для повторной попытки одной подцели проверьте, что появилось наблюдаемое изменение. `goal_progress.py` хранит только ограниченную сигнатуру: ID цепочки/подцели/стратегии, fingerprint репозитория и структурированный fingerprint evidence. Одинаковая сигнатура завершится с `NO_PROGRESS`; новый текст в поле evidence не является новым прогрессом.

```powershell
python .\goal_progress.py check .harness\work\<chain>.passport.json <subgoal-id> <strategy-id>
python .\goal_progress.py record .harness\work\<chain>.passport.json <subgoal-id> <strategy-id>
```

Исполняемый passport — это control DAG: только он открывает зависимости, назначает ownership и хранит состояние попыток. Graphify — отдельный локальный knowledge graph для поиска связей. Его вывод не меняет статус passport и сам по себе не является acceptance evidence: для перехода всё равно нужна свежая проверка или доказательство, зафиксированные в acceptance gate.

### Управление основной Goal

Один раз одобренная ограниченная цепочка выполняется до всех согласованных критериев: агент сам исследует, реализует, проверяет и исправляет в том же scope, без промежуточного «делай дальше». Для передачи нужен подготовленный пользовательский сценарий с наблюдаемым результатом; сборка не означает принятие пользователем или публикацию. Новые доступы, риск, внешние действия и расширение задачи по-прежнему требуют отдельного разрешения.

Текущий контекст — `.harness/CONTEXT.md` с указателем на единственный work item/passport, границей проверенного результата и следующим шагом. Проверяйте его branch/revision; читайте до пяти релевантных источников и расширяйте поиск под конкретный вопрос. Уже существующий Graphify — навигация к первичным файлам, а не второй журнал целей и не повод перечитывать все сессии.

В основном чате держите одну native Goal. Короткие измеримые части выполняются субагентами; отдельная видимая задача нужна только для долгого самостоятельного результата или безопасной границы контекста.

На старте/возобновлении основной Goal и после принятой подцели получите следующий безопасный план:

```powershell
python .\goal_orchestrator.py plan .harness\work\<chain>.passport.json --parent-state running
```

Для фактически приостановленной или заблокированной основной Goal передайте `paused` либо `blocked`. Команда только читает и валидирует passport. Она возвращает `launch`, `wait`, `verify`, `hold` или `complete`, но не нажимает Play, не создаёт задачи и не меняет статусы. `launch` применяется только после повторной проверки текущего passport; `verify` требует воспроизвести доказательства; `complete` не заменяет общую приёмку. При pause активная дочерняя работа доводится до безопасной контрольной точки — автоматический каскадный pause UI не предполагается.

Локальные `subgoal_blocked`/`agent_blocked` закрывают только затронутую ветку; `dependency_blocked` обозначает зависимый участок, `worktree_busy` — неизолированную запись. Независимый разрешённый `launch` может находиться в той же выдаче. Общая pause/block, отсутствие continuation authority и неисполняемый статус цепочки запрещают любой запуск. Проверка фактической изоляции checkout перед записью остаётся обязательной.

### Фильтр значимых обновлений

Для изменения Codex/GPT сначала проверьте свежий официальный источник и реальное локальное состояние. Зафиксируйте один кандидат по `templates/update-candidate.example.json`, не смешивая подтверждённые факты, выводы и допущения, затем выполните:

```powershell
python .\update_impact.py classify .\my-update-candidate.json
```

Классификатор работает offline, разрешает только официальные OpenAI documentation hosts и не исполняет текст источника. `significant` означает `run-local-evaluation`, а не автоматическое внедрение; `evaluate` требует дополнительных доказательств; `ignore` не создаёт работу. API-only возможность не считается доступной в локальном Codex без отдельной проверки. Радар не меняет одобренный профиль Luna/Astra автоматически; representative eval нужен до утверждений о выигрыше качества/скорости/расхода, а не для переопределения явно выбранной пользователем модели.

### Автономный наблюдатель обновлений

Scheduled Task собирает структурированный пакет только из четырёх официальных OpenAI Docs источников по инструкции `templates/update-radar-task.md`. Локальный watcher не ходит в сеть: он повторно валидирует пакет существующим классификатором и сохраняет ID/SHA-256, классификацию и ограниченную квитанцию локальной оценки; текст источников не хранится. Пример CLI (для теста используйте отдельный state, не живую историю):

```powershell
python .\update_radar.py scan .\templates\update-batch.example.json --state .harness\runtime\example-radar-state.json
```

Повтор не создаёт новую рекомендацию, но сохраняет незавершённые `pending` даже при пустом batch (`pending-evaluation`). Legacy v1 читается без записи, а отсутствие metadata оценки обозначается `evaluation-history-unknown`, не «оценено». После реальной проверки вызывайте `update_radar.py resolve <id> --digest <digest> --outcome <useful-or-no-benefit> --evidence-hash <sha256> --state <state>` по шаблону радара. Exact retry идемпотентен; `useful` — подтверждённое предложение, не внедрение; hash — квитанция, не автоматическое доказательство истинности. Без завершённой оценки resolve запрещён.

Изменившееся содержимое под прежним ID, повреждённое состояние, путь вне `.harness/runtime`, пакет более 64 кандидатов, история более 4096 ID или размер state более 1 MB отклоняются до записи. `ponytail:` backlog более 64 обрабатывается отдельно подтверждёнными пакетами; при `stateCount >= 3800` нужно предложить проверяемый archive/rotation, не удаляя историю. State атомарно заменяется, но рассчитан на **одного последовательного владельца**: scheduler и ручной scan/resolve нельзя запускать параллельно на одном файле. Межпроцессного lock нет; если сериализация не подтверждена, запись запрещена.

`meaningful-updates` означает только «проверить локально и предложить изменение». Watcher и Scheduled Task не редактируют код, не делают commit/push и не внедряют обновление. `no-meaningful-updates`: `Значимых обновлений для Harness нет.` — нет нового предложения, а не отмена прежней пользы. Неизменные pending/unknown остаются тихими; тяжёлую оценку повторяйте только после изменения prerequisites/evidence. Обновлённый локальный шаблон сам не меняет prompt действующей автоматизации; такое подключение требует отдельного согласования и проверки single-writer.

Сравнение имеет смысл только при валидных парах. Текущий in-memory compare ограничен 50 000 `pairKey`: локальный замер HRE-001 обработал этот предел за 1,763 с с пиком 54,06 MiB; при превышении архивируйте JSONL либо переходите на SQLite-индекс. Локальный benchmark — регрессионный оракул общей семантики качества, а не доказательство экономии токенов в реальных проектах или статистической значимости:

```powershell
python .\harness_benchmark.py --fixture .\tests\fixtures\hre-001-benchmark.json
```

Текущий профиль запрашивает до 12 субагентов плюс основной оркестратор. Это верхняя граница, а не обязательное число: фактическая параллельность зависит от доступных инструментов, лимитов Codex и безопасной изоляции файлов. Read-only задачи можно распараллеливать; для записи действует правило «один писатель на checkout/worktree».

Установка глобального навыка, ролей и managed `[agents]` блока:

```powershell
.\scripts\Install-GoalRunner.ps1 -WhatIf
.\scripts\Install-GoalRunner.ps1 -MaxConcurrentSubagents 12
.\scripts\Uninstall-GoalRunner.ps1 -WhatIf
```

Installer транзакционно обновляет глобальный config, подключает обязательную зависимость Context Handoff, отказывается смешиваться с неуправляемой секцией `[agents]` или чужими одноимёнными role-файлами и устанавливает четыре роли: lead, explorer, worker и verifier. Долговечный `~/.codex/goal-runner-install.json` хранит точные имена и хеши установленной версии. Старую установку без manifest можно принять явным `-AdoptMatchingLegacyRoles` при полном совпадении хешей. Для обновления проверенной ранней версии используйте более сильный `-AdoptVerifiedLegacyRoles`: каждый файл обязан быть валидным TOML, входить в фиксированный allowlist и содержать точное внутреннее имя роли. При сбое config, роли, manifest и созданные junction возвращаются в исходное состояние. Uninstaller сверяется с manifest, разрешает только четыре фиксированных пути внутри каталога agents, удаляет только управляемые артефакты Goal Runner и сохраняет общий Context Handoff. После установки перезапустите Codex или откройте новую сессию.

В git-проектах Goal Runner использует проверенные атомарные checkpoints: один commit после приёмки подцели, с chain/subgoal ID и сохранённым хешем в work item. Интеграцию коммитит основной оркестратор; worker получает право на commit только в отдельном чистом worktree. Автоматического push и широкого staging нет. Git-история дополняет, но не заменяет журнал решений и проверок.

При выполнении и code review действует [каноническая лестница](.agents/skills/goal-runner/references/laziness-ladder.md): сначала проверить возможность переиспользования, а для bugfix — первопричину и потребителей изменяемого контракта. Ревью всегда двухпроходное: correctness/security сначала, simplify/reuse/delete затем. Лестница не разрешает упрощать границы доверия, данные, деньги, безопасность, доступность, транзакции и явно запрошенное поведение.

## Что проверяет gate

Сначала запускайте адресный тест, затем соответствующий configured gate; не дублируйте его полный suite вручную в том же состоянии. Обязательные стадии и свежесть evidence сохраняются. В итог передавайте команду, результат, число тестов и время, а не весь успешный лог. Используйте существующие schema-1 метрики; без валидных реальных baseline/treatment пар экономия не измерена, неизвестные токены остаются `null`.

Gate проверяет обязательные артефакты, область git-диффа и признаки секретов; запускает только явно настроенные команды из `harness.config.json`, а не угадывает стек. Эти команды могут создавать изолированные тестовые артефакты, поэтому их побочные эффекты нужно проверить до запуска.

## Принципы

- **Нет доказательств — нет правки.** Не предполагать структуру, API или причину ошибки.
- **Малые обратимые шаги.** Один шаг должен иметь понятный ожидаемый эффект и проверку.
- **Гейт до, во время и после.** Ошибочное направление выявляется до массовых изменений.
- **Риск пропорционален проверкам.** Чем шире воздействие, тем сильнее валидация.
- **Сначала локальное, затем полное.** Это экономит время и токены без потери качества.

## Приватность Graphify

Graphify работает локально: код проекта не отправляется во внешние сервисы и не покидает рабочее окружение при анализе.

## Проверяемая приёмка

Для нетривиальных задач используйте `acceptance_gate.py`. В отличие от отметки «готово» в Markdown, он хранит durable JSON-критерии и повторно запускает каждую команду при проверке. Ручной критерий требует доказательство.

```powershell
python .\acceptance_gate.py init <work-item> --from .\my-acceptance.json
python .\acceptance_gate.py prove <work-item> review --evidence "Reviewed git diff."
python .\acceptance_gate.py check <work-item>
python .\acceptance_gate.py status <work-item>
python .\acceptance_gate.py reverify <work-item>
```

`status` только читает ledger и freshness: он не исполняет acceptance-критерии и не меняет ledger.
`check` и `reverify` исполняют все command criteria; для критерия можно объявить
`cwd` внутри корня проекта и `expect` с точной строкой успешного вывода. SHA-256
привязывает evidence к ID, типу, описанию критерия и параметрам команды. Изменение
определения делает PASS устаревшим. Старое command evidence требует `reverify`,
старое manual evidence — нового `prove`; это явно покажут `status` и отчёт задачи.
Если fingerprint проекта недоступен, `check` не запускает команду и не сообщает PASS,
а `prove` не записывает ручной PASS.

Подробный безопасный порядок подключения — в [docs/ADOPTION.md](docs/ADOPTION.md).

Проверяемое распространение одной версии между проектами описано в
[docs/DISTRIBUTION.md](docs/DISTRIBUTION.md): offline `harness_distribution.py`
и `scripts/Update-HarnessProjects.ps1` предоставляют preview, защищённое применение
18 core-файлов, сохранение backups и проверку версии/хешей. Глобальные skills,
локальные профили и активный scheduler не обновляются этой командой автоматически.

## Настройка проекта

Создайте `harness.config.json` по образцу `templates/harness.config.example.json` и укажите команды для `fastChecks`, `fullChecks`, а также пути, которые можно или нельзя менять. Команды запускаются только после явной настройки: harness не угадывает опасные команды.
