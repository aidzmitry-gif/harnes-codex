# Harness для агентной разработки

Этот репозиторий задаёт безопасный и экономный способ, по которому агент (и человек) ведёт разработку: сначала собирает доказательства, затем делает минимальное обратимое изменение и проверяет результат на уровне контракта, интеграции и регрессий.

Главная инструкция для агента — [AGENTS.md](AGENTS.md). Полная модель процесса — [docs/ENGINEERING_LOOP.md](docs/ENGINEERING_LOOP.md). Рабочие артефакты по каждой задаче сохраняются в `.harness/work/` и не должны попадать в коммиты с продуктовым кодом.

## Быстрый старт

1. Скопируйте `templates/work-item.md` в `.harness/work/<id>.md`.
2. Заполните цель, контракт, риски и критерии приёмки до первой правки.
3. Запустите предварительную проверку:

   ```powershell
   .\scripts\Invoke-HarnessGate.ps1 -Stage prechange
   ```

4. Внесите один минимальный вертикальный срез и запустите:

   ```powershell
   .\scripts\Invoke-HarnessGate.ps1 -Stage postchange
   ```

5. Перед передачей результата выполните `-Stage release` и заполните доказательства в work item.

## Передача контекста между задачами

Вызовите `$context-handoff`, когда задача стала длинной, уже сжималась или должна продолжиться в чистой задаче. Навык:

1. обновляет один канонический журнал проекта (`.harness/CONTEXT.md` по умолчанию или путь из локальных инструкций);
2. исключает transcript, скриншоты, browser state, полные логи и секреты;
3. показывает короткий title и стартовый prompt;
4. создаёт новую задачу только после подтверждения;
5. проверяет, что новая задача прочитала handoff, и только затем отдельно предлагает архивировать старую.

В утверждённой цепочке `$goal-runner` действует bounded chain mode: одно стартовое разрешение может покрывать чистые задачи-продолжения той же Goal. Предыдущие задачи становятся неактивными, но остаются открытыми до итоговой проверки; архивирование всей зарегистрированной цепочки выполняется только по отдельной финальной команде пользователя.

Не используйте fork для экономии контекста: он переносит историю исходной задачи. Канонический исходник навыка находится в `.agents/skills/context-handoff`; для работы во всех проектах подключите его в пользовательский каталог `~/.agents/skills/context-handoff` ссылкой или junction.

### Автонапоминание после compact

`scripts/Install-ContextHandoffReminder.ps1` устанавливает глобальный `SessionStart` hook с matcher `^compact$`. После ручного или автоматического сжатия hook добавляет только короткое напоминание предложить `$context-handoff`; он не читает transcript, не пишет project context и не создаёт/архивирует задачи.

Installer идемпотентен, проверяет TOML до замены и сохраняет исходный глобальный конфиг как `~/.codex/config.toml.bak-context-handoff-reminder`.

## Оркестрация большой Goal

`$goal-runner` превращает большую цель в DAG из измеримых подцелей. До запуска он показывает количество подцелей, ожидаемый результат каждой, зависимости, параллельные волны, роли/модели агентов, worktree ownership и проверки. После одного подтверждения оркестратор распределяет общий пул между готовыми подцелями, проверяет понимание task contracts, интегрирует доказательства и при необходимости продолжает Goal через `$context-handoff`.

Текущий профиль запрашивает до 12 субагентов плюс основной оркестратор. Это верхняя граница, а не обязательное число: фактическая параллельность зависит от доступных инструментов, лимитов Codex и безопасной изоляции файлов. Read-only задачи можно распараллеливать; для записи действует правило «один писатель на checkout/worktree».

Установка глобального навыка, ролей и managed `[agents]` блока:

```powershell
.\scripts\Install-GoalRunner.ps1 -WhatIf
.\scripts\Install-GoalRunner.ps1 -MaxConcurrentSubagents 12
.\scripts\Uninstall-GoalRunner.ps1 -WhatIf
```

Installer транзакционно обновляет глобальный config, подключает обязательную зависимость Context Handoff, отказывается смешиваться с неуправляемой секцией `[agents]` или чужими одноимёнными role-файлами и устанавливает четыре роли: lead, explorer, worker и verifier. Долговечный `~/.codex/goal-runner-install.json` хранит точные имена и хеши установленной версии. Старую установку без manifest можно принять явным `-AdoptMatchingLegacyRoles` при полном совпадении хешей. Для обновления проверенной ранней версии используйте более сильный `-AdoptVerifiedLegacyRoles`: каждый файл обязан быть валидным TOML, входить в фиксированный allowlist и содержать точное внутреннее имя роли. При сбое config, роли, manifest и созданные junction возвращаются в исходное состояние. Uninstaller сверяется с manifest, разрешает только четыре фиксированных пути внутри каталога agents, удаляет только управляемые артефакты Goal Runner и сохраняет общий Context Handoff. После установки перезапустите Codex или откройте новую сессию.

В git-проектах Goal Runner использует проверенные атомарные checkpoints: один commit после приёмки подцели, с chain/subgoal ID и сохранённым хешем в work item. Интеграцию коммитит основной оркестратор; worker получает право на commit только в отдельном чистом worktree. Автоматического push и широкого staging нет. Git-история дополняет, но не заменяет журнал решений и проверок.

При выполнении и code review действует лестница лени: YAGNI → stdlib/язык → нативный примитив платформы → существующая зависимость → одна строка → минимальный работающий код. Ревью всегда двухпроходное: correctness/security сначала, simplify/reuse/delete затем. Лестница не разрешает упрощать границы доверия, данные, деньги, безопасность, доступность, транзакции и явно запрошенное поведение.

## Что проверяет gate

Скрипт ничего не изменяет. Он проверяет наличие обязательных артефактов, чистоту/область git-диффа, секреты в изменениях и запускает подходящую стандартную проверку проекта, если она явно обнаруживается (`npm`, `pytest`, `dotnet`, `go`, `cargo`). Команды можно переопределить в `harness.config.json`.

## Принципы

- **Нет доказательств — нет правки.** Не предполагать структуру, API или причину ошибки.
- **Малые обратимые шаги.** Один шаг должен иметь понятный ожидаемый эффект и проверку.
- **Гейт до, во время и после.** Ошибочное направление выявляется до массовых изменений.
- **Риск пропорционален проверкам.** Чем шире воздействие, тем сильнее валидация.
- **Сначала локальное, затем полное.** Это экономит время и токены без потери качества.

## Приватность Graphify

Graphify работает локально: код проекта не отправляется во внешние сервисы и не покидает рабочее окружение при анализе.

## Проверяемая приёмка

Для нетривиальных задач используйте `acceptance_gate.py`. В отличие от отметки «готово» в Markdown, он хранит durable JSON-критерии и повторно запускает каждую команду при проверке. Ручной критерий требует доказательство.

```powershell
python .\acceptance_gate.py init <work-item> --from .\my-acceptance.json
python .\acceptance_gate.py prove <work-item> review --evidence "Reviewed git diff."
python .\acceptance_gate.py check <work-item>
```

Подробный безопасный порядок подключения — в [docs/ADOPTION.md](docs/ADOPTION.md).

## Настройка проекта

Создайте `harness.config.json` по образцу `templates/harness.config.example.json` и укажите команды для `fastChecks`, `fullChecks`, а также пути, которые можно или нельзя менять. Команды запускаются только после явной настройки: harness не угадывает опасные команды.
